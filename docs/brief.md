# Project Brief: Musinsa Wagon

## Executive Summary

**Musinsa Wagon**은 한국 패션몰의 **"가짜 할인"을 탐지하고 실제 가격 변동을 추적**하는 투명성 플랫폼입니다.

**핵심 문제:** 무신사, 에이블리, 지그재그 등 주요 패션몰은 명절 시즌마다 원가를 인위적으로 인상한 뒤 "대폭 할인" 마케팅을 펼칩니다. 20~30대 소비자들은 이런 속임수를 간파하고 싶지만, 개별 상품의 가격 히스토리를 수동으로 추적하기는 불가능합니다.

**핵심 솔루션:**

- 📊 **가격 히스토리 추적** - 30일/90일 최저가 및 평균가 대비 현재가 분석
- 🚨 **명절 속임수 탐지** - 명절 전후 가격 조작 패턴 자동 감지
- ⚡ **즉시 평가** - "지금 사도 되는 가격인지" 실시간 판단 (역대 최저가/좋은 딜/보통/비싼 편)
- ❤️ **찜 & 알림** - 사용자가 등록한 상품의 진짜 할인 시 알림

**기술 현황:**

- **Python 크롤러**: 무신사/에이블리/지그재그 크롤링 완료 (상품명, 브랜드, 이미지, 가격, 별점)
- **크롤링 전략**:
  - Daily 배치: 각 쇼핑몰 베스트 100개 + 카테고리별 50개 (총 ~450개/일)
  - 온디맨드: 사용자 찜/알림 등록 시 즉시 크롤링
  - MVP 출시 전 1개월간 사전 데이터 수집 예정
- **아키텍처**: Python 크롤러 → MySQL → Spring Boot API → Next.js 15 프론트엔드

**차별점:**

- 기존 가격 추적 서비스는 전자제품 중심 (쿠차, keepa) → **패션 카테고리 특화**
- 단순 가격 그래프 제공 → **한국 패션몰 마케팅 패턴 이해 및 탐지**
- 단일 플랫폼 추적 → **멀티 패션몰 통합 비교**

**프로젝트 성격:**
개발자 포트폴리오이자 실제 20~30대 패션 소비자에게 실용 가치를 제공하는 서비스. MVP는 핵심 가격 추적 인프라와 명절 속임수 탐지 알고리즘 검증에 집중합니다.

## Problem Statement

### 현재 상태와 고통 포인트

한국의 20~30대 패션 소비자들은 무신사, 에이블리, 지그재그 같은 온라인 패션몰을 일상적으로 이용하지만, **가격 투명성 부재**로 인해 반복적으로 손해를 보고 있습니다.

**구체적인 문제:**

1. **명절 마케팅 속임수**

   - 추석, 설날, 블랙프라이데이 등 대형 세일 기간 2주 전부터 정가를 인위적으로 인상
   - "최대 70% 할인" 홍보하지만 실제로는 원래 가격이거나 오히려 비싼 경우 다수
   - 소비자는 "역대 최저가"인지 "가짜 할인"인지 구분할 방법이 없음

2. **가격 변동 추적의 불가능성**

   - 한 소비자가 관심 있는 상품만 수십 개
   - 각 상품의 가격을 매일 수동으로 확인하는 것은 비현실적
   - 브라우저 북마크나 장바구니는 히스토리를 제공하지 않음

3. **플랫폼 간 분산**

   - 무신사, 에이블리, 지그재그 각각 찜 기능이 있지만 통합되지 않음
   - 같은 상품이라도 플랫폼마다 가격이 다를 수 있음
   - 멀티 플랫폼 비교가 불가능

4. **기회 비용 손실**
   - "지금 사야 하나?" vs "조금만 기다리면 더 싸질까?" 고민
   - 정보 부족으로 충동구매하거나, 최적 구매 타이밍을 놓침

### 문제의 영향 (정량화)

- **시장 규모**: 한국 패션 이커머스 시장 약 20조 원 (2024년 기준)
- **타겟 인구**: 20~30대 온라인 패션 소비자 약 800만 명
- **명절 세일 빈도**: 연 4~6회 (설날, 추석, 블프, 빼빼로데이 등)
- **평균 손실**: 소비자 1인당 연 10~30만 원 추정 (가짜 할인으로 인한 과다 지출)

### 기존 솔루션의 한계

**1. 쇼핑몰 자체 찜 기능**

- 가격 히스토리 제공 안 함
- 플랫폼 내에서만 작동 (크로스 플랫폼 불가)
- 알림이 있어도 "무조건 할인 시" 알림 (진짜/가짜 구분 없음)

**2. 가격 비교 사이트 (다나와, 에누리)**

- 전자제품/생활용품 중심, 패션 카테고리 약함
- 히스토리 제공하지만 패션몰 커버리지 낮음
- UI/UX가 20~30대 친화적이지 않음

**3. 해외 가격 추적 서비스 (keepa, CamelCamelCamel)**

- 아마존 전용 또는 해외 쇼핑몰 중심
- 한국 패션몰 미지원

### 왜 지금 해결해야 하는가?

1. **소비자 인식 증가**: MZ세대는 가성비와 투명성을 중시하며, 기업의 "속임수 마케팅"에 대한 불만이 커지고 있음
2. **기술적 실현 가능성**: 크롤링 기술 발전으로 멀티 플랫폼 데이터 수집이 가능해짐
3. **명절 세일 주기**: 곧 다가올 명절 시즌에 맞춰 론칭하면 즉시 가치 입증 가능
4. **포트폴리오 + 실사용**: 개발자에게는 풀스택 프로젝트 경험, 사용자에게는 실질적 금전적 이익 제공

## Proposed Solution

### 핵심 컨셉

**Musinsa Wagon**은 "가격 투명성"을 위한 **인텔리전스 레이어**로서, 단순히 가격을 보여주는 것을 넘어 **"이 가격이 좋은 딜인지"를 판단**해줍니다.

**포지셔닝:**

> "한국 패션몰 전문 가격 추적기 - 명절 마케팅 속임수를 꿰뚫는 쇼핑 인텔리전스"

### 솔루션 구성 요소

#### 1. 멀티 플랫폼 가격 추적 엔진

**기능:**

- 무신사, 에이블리, 지그재그 3개 플랫폼 통합 크롤링
- 일일 배치: 각 쇼핑몰 베스트 100개 + 카테고리별 50개 (총 ~450개 상품)
- 온디맨드: 사용자가 URL 등록 시 즉시 크롤링 및 추적 시작
- 수집 데이터: 상품명, 브랜드, 이미지, 현재가, 정가, 할인율, 별점

**사용자 가치:**

- 관심 상품을 한 곳에서 관리 (플랫폼 스위칭 불필요)
- 30일 이상 가격 히스토리 자동 축적

**차별점:**

- 각 쇼핑몰 찜 기능: 단일 플랫폼만 지원, 히스토리 없음
- Musinsa Wagon: **멀티 플랫폼 통합 + 자동 히스토리**

#### 2. 명절 속임수 탐지 알고리즘 (MVP 핵심)

**Level 1: 기본 가격 평가**

```
입력: 현재가, 30일/90일 히스토리
출력: 4단계 라벨
  🟢 역대 최저가 (히스토리 내 최저가 갱신)
  🟢 좋은 딜 (30일 최저가 or 평균 대비 10%↓)
  🟡 보통 가격 (평균 ±5%)
  🔴 비싼 편 (평균 대비 10%↑)
```

**Level 2: 명절 패턴 탐지** (핵심 차별점 - MVP 포함)

```
감지 패턴:
1. 명절 D-14일부터 정가 20% 이상 인상
2. 명절 당일 "할인가"가 원래 평균가 수준
3. 명절 후 7일 내 원가 복귀

→ 🚨 가짜 할인 의심 (명절 마케팅 패턴)
```

**예시 시나리오:**

- 평소가: 89,000원 (60일 평균)
- 추석 2주 전: 정가 149,000원으로 인상
- 추석 당일: "40% 할인" → 89,400원
- **Musinsa Wagon 판정:** 🚨 가짜 할인 (실제 할인율 0%)

**경쟁 비교:**

- 쿠차/keepa: 단순 가격 그래프만 제공, 패턴 해석은 사용자 몫
- Musinsa Wagon: **알고리즘이 자동 해석 및 경고**

#### 3. 실시간 구매 결정 지원

**상품 상세 페이지에서 제공:**

- 📊 가격 히스토리 그래프 (30일/90일/전체)
- 🏷️ 현재 가격 평가 라벨 (4단계)
- 📈 가격 트렌드 (상승/하락/안정)
- 🚨 명절 패턴 경고 (탐지 시)
- 💡 추천 액션: "지금 사세요" / "조금 더 기다려보세요" / "좋은 딜은 아님"

**차별점:**

- 기존 서비스: "할인 중입니다" (사실 확인)
- Musinsa Wagon: "실제로는 평소 가격이에요" (의미 해석)

#### 4. 스마트 찜 & 알림 시스템 (MVP)

**찜 기능:**

- 사용자가 상품 URL 등록 → 즉시 크롤링 및 추적 시작
- 멀티 플랫폼 통합 찜 리스트
- 각 상품의 실시간 가격 평가 상태 표시

**알림 기능 (푸시 알림):**

- 🟢 역대 최저가 갱신 시
- 🎯 사용자 설정 목표가 도달 시 (MVP 포함: "8만 원 이하 되면 알려줘")
- ⚠️ 가짜 할인 탐지 시 (ex. "지금 할인 중이지만 평소 가격이에요")

**차별점:**

- 기존: "할인 중" → 알림 남발 (노이즈)
- Musinsa Wagon: "진짜 할인" + "목표가 달성" → **의미 있는 알림만**

#### 5. 사용자 경험 (UX)

**핵심 플로우:**

1. **발견**: 패션몰에서 마음에 드는 상품 발견
2. **등록**: Musinsa Wagon에 URL 붙여넣기
3. **평가**: 즉시 현재 가격 평가 + 히스토리 확인
4. **결정**: "지금 살지 / 기다릴지" 데이터 기반 판단
5. **추적**: 찜 목록에서 관심 상품들의 가격 변동 모니터링
6. **알림**: 진짜 할인 또는 목표가 달성 시 푸시 알림

**디자인 원칙:**

- 20~30대 친화적인 모던 UI (Next.js + Tailwind CSS)
- 모바일 퍼스트 (패션 쇼핑은 주로 모바일)
- 시각적 명확성 (색상 라벨로 즉시 인지)

### 왜 이 솔루션이 성공할 것인가?

**1. 명확한 시장 공백**

- 패션 특화 + 멀티 플랫폼 가격 추적 서비스가 존재하지 않음
- 기존 서비스는 전자제품 중심 또는 단일 플랫폼 한정

**2. 실제 문제 해결**

- 단순 기능 제공이 아닌, "속지 않고 싶다"는 감정적 니즈 해결
- 금전적 이익 제공 (연 10~30만 원 절약 가능성)

**3. 기술적 우위 확보**

- Python 크롤러 구현 완료 (실현 가능성 검증됨)
- 패션몰 특화 알고리즘 (명절 패턴 이해)
- 1개월 사전 데이터 수집으로 론칭 시점부터 정확한 평가 가능

**4. 차별화된 포지셔닝**

- "가짜 할인 탐지"라는 명확한 메시지
- 한국 패션몰의 마케팅 관행을 이해하는 유일한 서비스

**5. 네트워크 효과 가능성**

- 사용자 증가 → 추적 상품 증가 → 서비스 가치 상승
- "이거 봐, 가짜 할인이었어!" 공유 가능성 (바이럴)

**6. 진입 장벽**

- 도메인 지식 축적 시간 필요 (한국 패션몰 마케팅 패턴)
- 히스토리 데이터 필요 (최소 1개월)
- 크롤링 노하우 (각 쇼핑몰 구조 파악)

### 장기 비전 (Post-MVP)

- 브랜드별 가격 패턴 분석 ("이 브랜드는 보통 언제 할인해요")
- 시즌 오프 예측 ("아우터는 2월에 가장 싸요")
- 커뮤니티 기능 (사용자들의 "진짜 할인" 공유)
- 더 많은 쇼핑몰 지원 (29CM, W컨셉 등)
- 브라우저 확장 프로그램 (클릭 한 번에 추적 등록)

## Target Users

### Primary User Segment: 가성비 중시 패션 소비자

**인구통계적 프로필:**

- **연령**: 20대 중반 ~ 30대 중반 (24~35세)
- **성별**: 여성 70%, 남성 30% (패션 쇼핑몰 이용 패턴 기반)
- **직업**: 직장인, 대학(원)생
- **소득**: 월 200~400만 원 (가처분 소득은 있지만 가성비 중시)
- **거주지**: 주로 수도권 (온라인 쇼핑 접근성 높음)

**현재 행동 및 워크플로우:**

- 무신사, 에이블리, 지그재그를 주 2~3회 이상 방문
- 출퇴근 시간, 점심시간에 모바일로 "둘러보기" 습관
- 평소에는 찜만 해두고, 명절/시즌 세일 기간에 구매 결정
- 여러 플랫폼을 오가며 가격 비교 (번거롭지만 어쩔 수 없이)
- 네이버, 카카오톡으로 친구들과 "이거 싸진 것 같아?" 공유

**구체적 니즈 및 고충:**

1. **정보 비대칭으로 인한 불안감**

   - "지금 할인 중인데, 정말 할인인가?"
   - "평소에도 이 가격 아니었나?"
   - "더 기다리면 더 싸지려나?"

2. **시간 부족**

   - 매일 가격을 일일이 확인할 시간이 없음
   - 여러 플랫폼을 오가는 것이 피곤함

3. **FOMO (놓칠까봐 두려움)**

   - "지금 안 사면 품절될까봐" 충동구매
   - 하지만 사고 나서 "더 싸게 살 수 있었는데..." 후회

4. **명절 마케팅에 대한 회의감**
   - "추석 대박 세일"이라고 하는데 믿음이 안 감
   - 과거에 속은 경험이 있어서 의심스러움

**달성하고자 하는 목표:**

- 💰 **금전적**: 불필요한 과다 지출 피하기, 진짜 할인 시에만 구매
- 🧠 **심리적**: "나는 똑똑한 소비자"라는 자신감, 속지 않는다는 안도감
- ⏰ **시간 절약**: 가격 추적을 자동화하여 쇼핑 의사결정 시간 단축
- 📱 **편의성**: 여러 플랫폼 찜 상품을 한 곳에서 관리

**페르소나 예시: 지현 (28세, IT 기업 직장인)**

> "저는 무신사에서 장바구니에 담아둔 아우터가 있었어요. 추석 세일 때 '50% 할인'이라고 해서 바로 샀는데, 나중에 친구가 '나는 한 달 전에 그 가격에 샀는데?'라고 하더라고요. 완전 속은 기분이었어요. 이제는 정말 할인인지 확인하고 싶어요."

**1단계: 문제 인식**

- 회원가입 (간단하게)

- 즉시 현재 가격 평가 확인 → "아, 지금은 비싼 편이구나"

- "이거 진짜 유용하네!" → 친구에게 추천

**6단계: 옹호자 (Advocate)**

- SNS나 커뮤니티에 "가짜 할인 적발" 사례 공유
- "Musinsa Wagon 덕분에 XX만 원 절약했어요!"

## MVP Scope

### Core Features (Must Have)

MVP에 반드시 포함되어야 하는 핵심 기능들입니다.

**1. 사용자 인증 시스템**

- 회원가입 / 로그인 / 로그아웃
- 간단한 프로필 관리 (이메일, 닉네임)
- **이유**: 사용자별 찜 목록과 알림 설정을 저장하기 위해 필수

**2. 상품 등록 및 추적 (온디맨드 크롤링)**

- 사용자가 상품 URL을 입력하여 추적 등록
- 지원 플랫폼: 무신사, 에이블리, 지그재그
- 등록 즉시 크롤링 실행 및 현재 상품 정보 표시
- **이유**: 서비스의 진입점, 사용자가 직접 원하는 상품 선택

**3. 일일 배치 크롤링 시스템**

- 각 쇼핑몰 베스트 100개 + 카테고리별 50개 자동 크롤링
- 사용자가 등록한 모든 상품 일 1회 크롤링
- 가격 변동 히스토리 DB 저장
- **이유**: 가격 히스토리 데이터 축적 및 패턴 분석 기반

**4. 가격 히스토리 시각화**

- 상품 상세 페이지에서 30일/90일 가격 그래프 표시
- 최저가, 최고가, 평균가 표시
- **이유**: 사용자가 가격 변동을 직관적으로 이해

**5. 가격 평가 알고리즘 (Level 1)**

- 30일/90일 평균 대비 현재가 분석
- 4단계 라벨링: 🟢 역대 최저가 / 🟢 좋은 딜 / 🟡 보통 / 🔴 비싼 편
- 상품 리스트 및 상세 페이지에 라벨 표시
- **이유**: 핵심 가치 제안, 사용자가 즉시 판단 가능

**6. 명절 속임수 탐지 알고리즘 (Level 2)**

- 명절 전후 가격 패턴 분석 (D-14일 ~ D+7일)
- 원가 급등 후 할인 패턴 감지
- 🚨 "가짜 할인 의심" 경고 표시
- **이유**: 핵심 차별화 요소, MVP의 정체성

**7. 찜 목록 관리**

- 사용자별 찜 목록 조회
- 찜 목록에서 각 상품의 현재 가격 평가 상태 표시
- 찜 해제 기능
- **이유**: 사용자가 관심 상품을 한 곳에서 관리

**8. 목표가 설정 기능**

- 상품별로 목표가 설정 ("8만 원 이하 되면 알려줘")
- 찜 목록에서 목표가 대비 현재가 표시
- **이유**: 사용자 요청 반영, 구매 결정 명확화

**9. 푸시 알림 시스템**

- 역대 최저가 갱신 시 알림
- 사용자 설정 목표가 달성 시 알림
- 가짜 할인 탐지 시 경고 알림
- 알림 ON/OFF 설정 (상품별, 전체)
- **이유**: 핵심 가치 전달 수단, 사용자 재방문 유도

**10. 모바일 반응형 UI**

- 모바일 퍼스트 디자인
- 20~30대 친화적 모던 UI (Tailwind CSS + shadcn/ui)
- 색상 라벨로 즉시 인지 가능한 시각적 명확성
- **이유**: 타겟 사용자의 주 사용 환경

### Architecture Considerations

#### Repository Structure

**Multi-repo (각 서비스 독립 관리):**

- `musinsa-wagon-crawler` (Python) - 크롤러 전용 리포지토리
- `musinsa-wagon-backend` (Spring Boot) - API 서버
- `musinsa-wagon-nextjs-react-ts-v2` (Next.js) - 프론트엔드 (현재 리포지토리)

**이유:**

- 각 서비스 독립 배포 가능
- 기술 스택이 명확히 분리됨
- 포트폴리오 시 각각 보여주기 용이
- CI/CD 파이프라인 독립 관리

#### Service Architecture

**3-Tier Architecture:**

```
[Python Crawler] → [MySQL] ← [Spring Boot API] ← [Next.js Frontend]
       ↓                           ↓
   (Direct Write)            (Read + Algorithm)
       ↓                           ↓
   [Price History]          [FCM Push Notification]
```

**데이터 플로우:**

1. **사용자 상품 등록 (온디맨드 크롤링):**

   - Next.js → Spring API (`POST /api/products`) → MySQL (products 테이블)
   - Spring → Python 크롤러 트리거 (즉시 크롤링)
   - Python → MySQL 직접 Write (price_history 테이블)

2. **일일 배치 크롤링:**

   - Spring Scheduler (매일 새벽 2시) → Python 크롤러 호출 또는 cron
   - Python → 베스트/카테고리 상품 + 사용자 찜 상품 크롤링
   - Python → MySQL 직접 Write (price_history 테이블)

3. **가격 평가 및 알림:**

   - Spring Scheduler (매일 오전 9시) → 가격 변동 분석
   - 명절 패턴 탐지, 역대 최저가 확인, 목표가 도달 확인
   - Spring → Firebase Cloud Messaging (FCM) → 사용자 푸시 알림

4. **사용자 조회:**
   - Next.js → Spring API (`GET /api/products/:id/history`)
   - Spring → MySQL 조회 → 가격 평가 알고리즘 실행 → Next.js

#### Integration Requirements

**Spring ↔ Python 연동:**

- **방식**: Python이 MySQL에 직접 Write (PyMySQL/SQLAlchemy)
- **Spring 역할**: Read 전용, 가격 평가 알고리즘 실행
- **Python 트리거**: Spring에서 시스템 명령어 또는 별도 cron

**Next.js ↔ Spring 연동:**

- **방식**: REST API (JSON)
- **주요 엔드포인트**:
  - `POST /api/auth/register` - 회원가입
  - `POST /api/auth/login` - 로그인 (JWT 반환)
  - `POST /api/products` - 상품 등록 (크롤러 트리거)
  - `GET /api/products/:id` - 상품 조회 (가격 평가 포함)
  - `GET /api/products/:id/history` - 가격 히스토리 (30일/90일)
  - `GET /api/watchlist` - 찜 목록 조회
  - `POST /api/watchlist` - 찜 추가
  - `DELETE /api/watchlist/:id` - 찜 해제
  - `PUT /api/watchlist/:id/target-price` - 목표가 설정

**푸시 알림:**

#### Security/Compliance

## Risks & Open Questions

### Key Risks

#### 1. 크롤링 차단 리스크 (🔴 Critical)

**리스크:**

- 무신사, 에이블리, 지그재그가 크롤링을 차단 (IP 밴, Cloudflare, rate limit)
- 쇼핑몰 구조 변경으로 크롤러 작동 중단

**영향:**

- 프로젝트 전체 실현 불가 (핵심 데이터 수집 불가)

**가능성:** 중간 (30%)

- Python 크롤러 이미 작동 검증됨
- 하지만 프로덕션 환경에서 대규모 크롤링 시 차단 가능성

**완화 전략:**

1. **User-Agent 설정**: 정상 브라우저로 위장
2. **크롤링 빈도 제한**: 과도한 요청 방지 (polite crawling)
3. **프록시 로테이션**: IP 밴 시 프록시 사용 (비용 발생)
4. **API 탐색**: 공개 API 존재 여부 확인 (무신사 등)
5. **대체 전략**: 차단 시 해당 쇼핑몰 제외, 다른 몰 추가

**대응 계획:**

- M1 (인프라 완성) 시점에 프로덕션 환경에서 1주일 테스트
- 차단 발생 시 즉시 완화 전략 적용
- 3개월 이상 지속 차단 시 프로젝트 피벗 고려
